# 压缩农业系统 · Spec

> 平台：Minecraft 1.21.1 / NeoForge 21.1.235
> 术语表：`GLOSSARY.md`。决策依据：`docs/adr/0001`–`0015`。完整方案：`docs/plan-v2.0.md`。
> 本 spec 只用术语表里的词。凡是 ADR 已定的，这里不重新论证，只引用。

---

## Problem Statement

玩家在 Minecraft 里经营农田时，面临三个重复劳动：

1. **收获要一格一格点。** 一片 9×9 的麦田，成熟后要右键 81 次。
2. **补种要一格一格点。** 收完还要再点 81 次，才能让地继续产出。
3. **产量被面积锁死。** 想增产只能扩地，扩建意味着更多的重复劳动，而不是更好的回报。

原版没有任何机制把「一片田」当成一个整体来管理。箱子能堆物品，但不能堆**正在生长的地**。

结果是：玩家想搞大农业，得到的惩罚是更多的点击，而不是更高效的产出。

---

## Solution

压缩农业把**耕地本身**压缩。

9 个方块合成 1 个压缩方块。压缩方块分两形态（压缩泥土 / 压缩耕地）和 9 个等级。等级 `L` 决定收获倍率 `9^L`：一个 L=3 的压缩耕地上长出一株小麦，产物不是 1 份，是 `729` 份，直接写进压缩方块自己的 27 格货仓。

**玩家操作没有任何新东西。** 空手右键收作物、锄头右键犁地、骨粉催熟、种树苗 —— 全部是原版行为。压缩方块只是让这些原版行为的**产物归到货仓里并乘倍率**，而不是掉在地上。

三件事因此同时解决：

- **收获**：作物成熟被事件拦截，产物自动进货仓，玩家不用点
- **补种**：结算成功后幼苗自动重置，下一轮继续
- **产量**：用等级换取倍率，而不是用面积换取点击次数

树木和蘑菇同理：树苗长成树后整棵被枚举、逐方块取真实掉落、乘倍率写入货仓、原地回填树苗。蘑菇骨粉催成蘑菇树后走同一套。

**一个压缩方块只承载一个作物，与普通耕地完全等价。** 压缩带来的不是「一格种很多」，而是「一格产出很多」。这是本模组与「密植」类模组的根本区别。

## User Stories

### 压缩方块与合成

1. 作为玩家，我想用 9 个泥土合成 1 个 1 级压缩泥土，这样我就有了压缩农业的起点。
2. 作为玩家，我想用 9 个低等级压缩方块合成 1 个高等级压缩方块，这样我能提高倍率。
3. 作为玩家，我想看到压缩方块当前是第几级，这样我能判断倍率是多少。
5. 作为玩家，我想把压缩泥土变成压缩耕地，这样我能在上面种作物。
6. 作为玩家，我想在形态转换时保留货仓里的东西，这样我不会因为一次常规操作丢掉积累的产出。
7. 作为玩家，我想让压缩方块能被活塞推动，这样我能用红石自动化布置农田。
8. 作为玩家，我想在活塞推动时保留货仓内容，这样自动化不会让我丢东西。
9. 作为玩家，我想在破坏压缩方块时拿到货仓里的东西，这样我不会因为拆地而损失产出。
10. 作为玩家，我想让压缩方块有和普通泥土一样的挖掘速度与工具需求，这样它不会有奇怪的获取门槛。

### 压缩耕地与作物

11. 作为玩家，我想把原版作物种在压缩耕地上，这样我不需要学习新的种植方式。
12. 作为玩家，我想在作物成熟时自动收获，这样我不需要一格一格点。
13. 作为玩家，我想在自动收获后自动补种，这样地能持续产出。
14. 作为玩家，我想让收获产物按 `9^L` 乘倍率，这样高等级压缩耕地值得投资。
15. 作为玩家，我想让高等级压缩耕地一次收获就能装满货仓，这样我能感受到等级带来的量变。
16. 作为玩家，我想让模组作物也能种在压缩耕地上，这样整合包里不会只有原版作物能用。
17. 作为整合包作者，我想通过标签决定哪些方块算「可压缩作物」，这样我不需要改代码就能兼容其他模组的作物。
18. 作为玩家，我想让骨粉催熟的作物也被正常收获，这样骨粉不会白用。
19. 作为玩家，我想让骨粉催熟到一半（未成熟）的作物不被误收，这样骨粉可以正常分次使用。
20. 作为玩家，我想让货仓满了的时候作物保持在成熟状态，而不是被重置成幼苗，这样我不会白烧一轮产出。
21. 作为玩家，我想在货仓腾出空间后，成熟作物能被补收，这样我不需要手动再催一次。
22. 作为整合包作者，我想在作物掉落表为空时看到明确的警告日志，这样我能发现是配置错了。

## Implementation Decisions

### 模块划分

| 模块 | 职责 | 依赖方向 |
|---|---|---|
| **统一入口** `settle` | 乘倍率、原子性检查、写货仓。纯函数，不读世界 | 被所有收获模块调用 |
| **货仓** `CompressedBlockEntity` | 27 格存储、序列化、容量约束 | 被 `settle` 通过接口访问 |
| **作物模块** | 事件监听 → 取掉落 → 调 `settle` | → 统一入口 |
| **树木模块** | 真实生成 → 连通性枚举 → 逐方块取掉落 → 调 `settle` → 拆除 → 回填 | → 统一入口 |
| **蘑菇模块** | 骨粉催树 → 复用树木模块的枚举与拆除 → 回填 | → 树木模块 |
| **瓜类模块** | `StemBlock` Mixin → 取 `fruit` → 调 `settle` | → 统一入口 |
| **方块注册** | 18 方块 + BE + 标签 + 合成 | 无 |

### 统一入口的接口契约

`settle` 是本模组的核心。按 ADR-0006，它**显式接收 `L`**，内部不反查坐标：

```
settle(drops: List<ItemStack>, level: int L, target: ChestTarget) → SettlementResult
```

`ChestTarget` 是一个窄接口，把 `CompressedBlockEntity` 抽象掉，使 `settle` 可脱离游戏测试：

```
ChestTarget:
  capacityPerSlot() → long        // = 64 × (1 + chestCount)
  tryReserve(item, amount) → boolean   // 原子预留
  commit()                         // 预留转正式写入
  rollback()                       // 放弃全部预留
```

`SettlementResult` 为三值枚举：`SUCCESS` / `INSUFFICIENT_SPACE` / `INVALID_INPUT`。

**为什么这样切**：ADR-0003 说等级与容量正交，ADR-0005 说容量失败不惩罚作物，ADR-0007 说空掉落要 WARN。这三条都落在 `settle` 的边界上。把它做成纯函数后，这三条能被 JUnit 直接测，不需要启动游戏。

### 倍率与溢出

按 §9：

- 每种物品 `Math.multiplyExact(count, 9^L)`
- 捕获溢出 → 按 `INSUFFICIENT_SPACE` 处理，**不静默截断**
- `9^L` 预先用 `long` 计算，`L ∈ [1, 9]`，最大 `387,420,489`
- `stackLimit = 64 × (1 + chestCount)` **必须用 `long`**：`chestCount` 接近 `MAX_CHEST_COUNT`（`1e9`）时 `int` 会溢出

### 原子性

ADR-0005：`INSUFFICIENT_SPACE` 是**全有或全无**。任一物品放不下 → 一个都不写 → 作物保持成熟态。

因此 `ChestTarget` 提供 `tryReserve` / `commit` / `rollback` 三阶段，而不是「试着写、写不进就回退已写的部分」——后者在多方块场景下容易漏回退。

### 货仓数据

按 §10：

```
schemaVersion: int = 1
chestCount: long
slotItems: ResourceLocation[27]
counts: long[27]
```

- 无 `cropId` 字段
- `counts[i] == 0` 时 `slotItems[i] = null`
- 加载时 `chestCount` clamp 到 `[0, MAX_CHEST_COUNT]` 并 `setChanged()`
- 形态转换与活塞迁移**共用同一套搬运代码**（ADR-0002）

### 作物模块的两条触发路径

按 ADR-0001：

- **路径 A**：`CropGrowEvent.Post` → 检测 `getNewState()` 成熟 → 调 `settle`
- **路径 B**：`BonemealEvent` → 只记录 `(dimension, pos)` 到本 tick 集合 → `ServerTickEvent.Post` 遍历 `getAllLevels()` 读实际状态 → 成熟则调 `settle`

路径 B 的约束（均已验证）：

- `BonemealEvent` **无 Post 变体**，且触发点在 `performBonemeal` 之前
- 监听器**不取消**、**不调 `setSuccessful`**
- 客户端也会触发，必须 `if (!(level instanceof ServerLevel)) return`
- 集合键用 `ResourceKey<Level>` + `BlockPos.asLong()`，每 tick 无条件清空

按 ADR-0009，识别时先排除 `instanceof StemBlock`，再走标签 / `CropBlock` 判定。

### 树木模块

按 ADR-0011（参考 Create `TreeCutter`）：

1. 允许原版 `growTree` 正常执行
2. 从树苗位置向上找树干，BFS 连通性遍历，分三类：
   - `logs`：`BlockTags.LOGS` / `SLIMY_LOGS` / `MUSHROOM_STEM`
   - `leaves`：任何有 `distance` 整数属性且非 `STABILITY_DISTANCE` 的方块；蘑菇块 / 菌岩按固定半径（红菇 2、褐菇 3）
   - `attachments`：`TREE_ATTACHMENTS`
3. `validateCut` 检查被砍位置上方是否还有不依附本层的原木
4. 逐位置 `Block.getDrops(state, serverLevel, pos, blockEntity, player, tool)`
5. 汇总调 `settle`
6. 所有位置设为空气
7. 按 ADR-0014 回填：单格放一棵树苗，2×2 放四格，`STAGE = 0`

**无方块数上限**。`visited` 集合保证每个位置只进一次，遍历受区块加载边界天然约束。不设人为截断——截断会让巨型树静默少给产物。

**不触发玩家破坏事件**（`BreakEvent` / `BlockDropsEvent`）：我们不是玩家破坏，不应加经验、统计、成就。

### 蘑菇模块

按 ADR-0013 与 ADR-0015：

- **路径一**：骨粉 → 原版 `growMushroom` → 复用车模块的枚举与拆除 → `settle` → 原位回填一个同种蘑菇
- **路径二**：随机扩散保持原版约束（光照 < 13、9×9×3 内同种 < 5 朵），不加速
- 压缩方块**不加入** `MUSHROOM_GROW_BLOCK`，因此仍受光照约束（ADR-0013）

### 瓜类模块

按 §7：

- Mixin 注入 `StemBlock.randomTick` 与 `performBonemeal`
- **前提**：压缩方块已加入 `#minecraft:dirt`（ADR-0010），否则 `StemBlock` 的 `FARMLAND || DIRT` 检查恒 false
- `@Accessor` Mixin 读取 `private final ResourceKey<Block> fruit`
- 失败时保留 `AGE=7`、不消耗茎

### 多格植物截顶

压缩耕地上的多格植物（甘蔗 / 仙人掌 / 竹子）**只保留 1 格高度**（ADR-0021）。

- **判定**：第 2 格与第 1 格是**同一方块**，第 1 格属于 `#compressedagriculture:multi_block_plants`，第 2 格下方 2 格是压缩耕地。同方块判定是必须的——树苗长成原木、蘑菇长成菌柄都是「不同方块」，不这样挡会直接把树木 / 蘑菇模块拆掉
- **触发**：`BlockBehaviour#onPlace` 里只记录坐标（`LevelChunk.setBlockState` 对每次方块变更都会调它），`ServerTickEvent.Post` 统一结算与拆除。不在 `onPlace` 里当场动手，避免重入
- **结算**：第 2 格的原版掉落 × `9^L` 写进脚下压缩耕地的货仓，然后只拆第 2 格，第 1 格保留
- **停摆**：`INSUFFICIENT_SPACE` 时第 2 格原样保留，不拆不写，等玩家腾出空间
- **已知副作用**：玩家手动往压缩耕地上堆第 2 格也会被拆走——「这块地上只保留 1 格」

#### 例外：紫颂（ADR-0022）

紫颂不能走上面的「同方块」规则：它长高时第 1 格变成 `chorus_plant`、第 2 格是 `chorus_flower`，**两种不同方块**。它走同一条管线（`onPlace` 记录 + tick 末处理）的单独一支：

- **判定**：新方块是紫颂花、脚下那格是紫颂茎、脚下 2 格是带 BlockEntity 的压缩耕地。按方块**类型**判定（`ChorusFlowerBlock` / `ChorusPlantBlock`），不写方块 ID、不新建标签
- **整株结算**：底座那格（`chorus_plant` → 紫颂果 0–1）和顶花那格（`chorus_flower` → 自身 1）都查战利品表，合并成一份清单 × `9^L`
- **虚拟实体**：两次查询都带 `LootContextParams.THIS_ENTITY = FakePlayerFactory.getMinecraft(level)`。`chorus_flower` 的掉落表带 `entity_properties(entity = "this")` 条件，没有实体就恒为空清单 → `INVALID_INPUT` → 植株永久卡死
- **回填**：`SUCCESS` 时把底座和顶花两格都设为空气，然后在**底座位置**回填一朵 `AGE = 0` 的紫颂花（先拆后填、不从产物里扣）。不置 0 会从收下来那朵的年龄继续，很快变成 `AGE = 5` 的死花
- **停摆**：`INSUFFICIENT_SPACE` 时**整株**原样保留（不拆、不回填）；`INVALID_INPUT` 不拆不回填、WARN
- **已知限制**：紫颂横向分枝不处理（分枝出的花悬空，不在第 2 格位置上）

### 重试时机

按 ADR-0005，三处驱动，均不轮询：

1. 玩家关闭本模组 menu（`PlayerContainerEvent.Close`）→ 该 BE 上方 3×3 尝试一次
2. 玩家右键该压缩方块
3. 玩家破坏该压缩方块前

约束：menu 必须继承 `AbstractContainerMenu`，否则收不到第 1 条。

## Testing Decisions

### 什么算好测试

只测**外部行为**，不测实现细节。

- 测 `settle(drops, L, target)` 返回什么、`target` 里最终存了什么
- 不测 `settle` 内部用了几个循环、调了几次 `tryReserve`
- 测「一棵树被枚举出的位置集合是否等于树」，不测 BFS 的队列类型

判据：**重构内部实现时，测试不该改。**

### Seam 1：`settle` 纯函数 — JUnit

**这是唯一新增的 seam。** 需要：

- 给工程加 JUnit 依赖（模板 `build.gradle` 没有）
- 一个 `ChestTarget` 的内存实现 `FakeChest`（固定容量，记录写入）

覆盖的用例：

| 用例 | 期望 |
|---|---|
| 单物品 × `9^1` | `SUCCESS`，数量 ×9 |
| 单物品 × `9^9` | `SUCCESS`，数量 ×387,420,489 |
| 计数 × `9^9` 溢出 `long` | `INSUFFICIENT_SPACE`，`target` 无变化 |
| 多物品，其中一个放不下 | `INSUFFICIENT_SPACE`，**所有**物品都没写入 |
| 空掉落清单 | `INVALID_INPUT` |
| `chestCount = 0` | 每格上限 64 |
| `chestCount = MAX` | `stackLimit` 不溢 `int` |
| 同物品优先同槽 | 占一个槽而不是两个 |

### Seam 2：`TreeHarvester.enumerate` — GameTest

**必须现在写**。ADR-0011 是推理出来的、没验证过的。

用例：

| 用例 | 期望 |
|---|---|
| 种一棵橡树苗，`growTree` 后枚举 | `logs` 非空、`leaves` 非空 |
| 在树中间砍一格，调 `validateCut` | 返回 `false` |
| 从树根砍，调 `validateCut` | 返回 `true` |
| 巨型蘑菇树枚举 | `MUSHROOM_STEM` 进 `logs`，蘑菇块进 `leaves` |
| 枚举结果去重 | 同一位置不出现两次 |

GameTest 用模板已内置的 `gameTestServer` 运行配置，`neoforge.enabledGameTestNamespaces` 设为 `compressedagriculture`。

### Seam 3：不测的部分

| 不测 | 理由 |
|---|---|
| `CropGrowEvent.Post` / `BonemealEvent` 时机 | 事件顺序是静态事实，已通过查 NeoForge sources 确认；tick 级测试脆弱且昂贵 |
| 瓜类 Mixin 注入点 | 注入点是编译期事实，靠反编译确认 |
| `#minecraft:dirt` 五条副作用 | 玩法验收，不是自动化测试 |
| GUI 渲染 | 无自动化价值 |
| 合成配方 | 数据驱动，人工验证 |

### Prior art

仓库目前无既有测试，无从参考。模板 `mdk-1.21.1-neoforge` 带 `gameTestServer` 运行配置但未含任何 test 源。因此本 spec 是**建立测试基线**，不是沿用。

## Out of Scope

- **加速生长**：任何让作物 / 树 / 蘑菇长得更快的东西。ADR-0014 明确保留原版节奏。
- **密植**：一个压缩方块承载多个作物。一个压缩方块 = 一个作物。
- **自动播种新种子**：只在原地重植原来那株，不从货仓消耗种子。
- **工具 / 耐久**：本模组不引入任何新工具。
- **多方块结构**：压缩方块都是单方块。
- **跨维度 / 跨方块传输**：货仓只能手动取或通过 GUI 取。
- **能量 / 流体**：纯物品。
- **自定义作物 / 树木 / 蘑菇的内容**：本模组不加任何新作物，只压缩原版和模组已有的。
- **服务端 / 客户端不同步的优化**：先按标准 `CustomPacketPayload` 走。

## Further Notes

### 未决的实现细节（不阻塞 spec，实现时定）

1. **`validateCut` 的精确判据**：Create 的实现依赖它的 `pos` 语义。我们需要确认「从树苗位置调」还是「从树干位置调」才是正确入口。
2. **枚举与拆除的区块边界**：树可能跨区块，`ServerLevel.getBlockState` 在未加载区块上返回空气。需要决定是跳过还是强制加载。
3. **回填与拆除的顺序细节**：ADR-0014 要求先拆后填，但 2×2 的四格回填需确认不会被自身拆除逻辑命中。

### 与 v1.9.2 的关键差异

| v1.9.2 | v2.0 |
|---|---|
| `tree_loot` 手工映射 | 真实生成 + 连通性枚举 |
| `BlockTags.CROP` | `BlockTags.CROPS` |
| `BonemealEvent` 内前后对比 | `ServerTickEvent.Post` 观察 |
| `INSUFFICIENT_SPACE` 重置幼苗 | 保留成熟态 |
| 蘑菇只有扩散 | 骨粉催蘑菇树为主要收益 |

### 风险最高的三处

1. **ADR-0010 的 `#dirt` 副作用**：五条待确认项可能带来意外行为，尤其是草蔓延覆盖压缩泥土。
2. **ADR-0011 的枚举正确性**：`isLeaf` 靠 `distance` 属性探测，在模组树叶上的表现未验证。
3. **`9^L` 溢出**：L=9 时一次结算就可能顶到 `MAX_CHEST_COUNT`，边界用例必须覆盖。

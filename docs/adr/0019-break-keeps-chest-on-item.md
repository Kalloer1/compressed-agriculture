# 0019 · 破坏压缩方块时货仓随方块物品走，不散落成掉落物

- 状态：已采纳（2026-10-31）
- 影响面：ticket 03b（已实现）、ticket 09（破坏掉落一节）
- 澄清：spec 用户故事 9「破坏压缩方块时拿到货仓里的东西」与 plan §11.4「破坏 NBT 保留」的歧义

## 背景

两处文档对「拆掉压缩方块时货仓里的东西去哪」有两种读法：

- spec 故事 9：「我想在**破坏压缩方块时拿到货仓里的东西**，这样我不会因为拆地而损失产出。」
- plan §11.4：「存储、加载校验、**破坏 NBT 保留**。」

前者读起来像「内容物散落成 `ItemEntity`」，后者读起来像「物品带着 NBT」。ticket 03b 按后者实现（掉落物携带 `BLOCK_ENTITY_DATA`），ticket 09 的验收标准按前者写成「货仓里的全部内容作为掉落物给玩家」。两者不能同时成立。

## 决策

**采用「随方块物品走」**：破坏压缩方块 → 掉落的方块物品携带完整货仓数据（`schemaVersion` / `chestCount` / 27 格）；放下时原样恢复。**不额外散落 `ItemEntity`。**

## 理由

1. **数量级不允许散落**。`stackLimit = 64 × (1 + chestCount)`，`chestCount` 上限 10 亿 → 单格最多 640 亿个物品。散落成实体就是瞬间几百万个 `ItemEntity`，服务端直接跪。这不是「性能优化」，是可行性问题。
2. **原版先例**：潜影盒就是「破坏时内容随物品走」。玩家对这套语义已有认知，不需要教学。
3. **故事 9 的诉求是「不损失」**，不是「必须掉在地上」。物品带着内容走同样满足「不会因为拆地而损失产出」，而且搬运/重建更可靠。
4. **与活塞迁移、形态转换共用同一套搬运代码**（ADR-0002）。三者都是「把一个 BE 的数据搬到另一个位置」，散落方案反而会引入第三套路径。

## 备选方案

1. **散落成 `ItemEntity`**：见理由 1，放弃。
2. **散落到玩家背包，溢出才掉地上**：仍然要处理 640 亿的数量级，且玩家背包容量是 36 格 × 64。放弃。
3. **破坏时弹出 GUI 让玩家分批取**：破坏方块弹界面是反直觉的交互，且与「活塞推动」「形态转换」不共用代码。放弃。

## 后果

- ticket 09 的「破坏掉落」一节标记为 **由 03b 完成**，09 不再重复实现。
- 玩家想取出内容物，需要把方块放下来再打开 GUI（ticket 08）。
- `CompressedBlockEntity.saveData` / `loadData` 是唯一的搬运入口，活塞迁移（09b）与形态转换（09a）都必须走它。

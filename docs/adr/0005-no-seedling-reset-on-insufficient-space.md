# 0005 · 货仓满时不重置幼苗，保留成熟态等待下次结算

- 状态：已采纳（2026-10-31）
- 影响面：§5.6 失败语义、§9 统一写入入口、§7.2 瓜类失败分支
- 取代：方案 v1.9.2 §5.6 中「`INSUFFICIENT_SPACE` → 整体丢弃并**重置幼苗**」一句

## 背景

方案 v1.9.2 §5.6 规定：

> - `INSUFFICIENT_SPACE`：不写入，不生成 `ItemEntity`，整体丢弃并**重置幼苗**（两条触发路径一致）。

## 问题

货仓满 → 作物长熟 → 结算失败 → 苗被设回 `age = 0`。玩家看到的是刚长熟的地又变回青苗，这一轮的收成凭空消失。这个循环每轮重复，直到玩家想起来去清货仓。

而 ADR-0003 已经确立：高等级配低容量是**合法配置**，`INSUFFICIENT_SPACE` 会频繁触发。把「合法的配置选择」惩罚成「作物数据丢失」，等于让玩家在没收到任何警告的情况下每轮损失 `9^L` 份产出——L=9 时是 3.87 亿份的量级，远谈不上可接受。

## 决策

`INSUFFICIENT_SPACE` 时**不重置幼苗**，保留成熟态。

下次有玩家打开该货仓 / 货仓腾出空间时，同一位置下一次成熟检测会重新尝试结算，成功后照常重置。

瓜类（§7.2）已采用同构语义（保留 `AGE=7`、不消耗茎），本次决策让普通作物与之对齐。

## 理由

- **失败原因是容量，不是作物**。用作物惩罚玩家的扩容决策，是错误的归因。
- **对齐同文档内的既有设计**。§7.2 瓜类「失败时不消耗茎、保留 `AGE=7`」已经是「失败不损失」的写法，普通作物没理由反着来。
- **`INVALID_INPUT` 已经给出了「不重置」的先例**（§5.6）。同一节里两种失败给出相反的补偿，本就没有原则可言。
- 保留成熟态意味着**可见的待办**：地一直是熟的，玩家会注意到并去清货仓。重置幼苗则把问题变成静默的。

## 备选方案

1. **照原文重置**：放弃，理由见上。
2. **重置但发提示**：提示只能告知损失，不能挽回。且每轮都提示一次会变成刷屏噪音。放弃。
3. **结算失败时溢出到 `ItemEntity` 掉在地上**：等于绕过容量限制，货仓失去意义，且大数量会炸服务端。放弃。

## 后果

- 成熟且货仓满的作物会一直保持成熟态。`CropGrowEvent.Post` 不会重复触发（已成熟），因此**不存在 tick 风暴**——只在有事件驱动时重试。
- 需要一条独立的「重试时机」。已验证：`CropBlock.isRandomlyTicking(state)` 返回 `!isMaxAge(state)`，所以成熟作物**根本不再进入随机刻**，`CropGrowEvent.Post` 不会因为它保持成熟而反复触发。重试必须由外部驱动。

### 重试时机（三处，按代价从小到大）

1. **玩家关闭该 BE 的 GUI**：挂 `PlayerContainerEvent.Close`，对 `pos` 上方 3×3 范围尝试一次结算。这是主路径。
2. **玩家右键该压缩方块**：交互时顺带尝试一次。
3. **玩家破坏该压缩方块前**：`playerWillDestroy` 里尝试一次，避免「拆了地却丢了熟作物」。

三处都不做定时轮询。`PlayerContainerEvent.Close` 携带的是 `AbstractContainerMenu`，因此本模组的 menu 必须**继承 `AbstractContainerMenu`** 才能收到这个事件——如果为了省事写了个不走标准 menu 的自定义 GUI，这条重试路径就丢了。
- 瓜类与普通作物共用这套重试逻辑，不再各写一份。
- 文档 §5.6 需同步修正。

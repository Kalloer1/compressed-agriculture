# 0014 · 树苗保留两阶段生长，拆树后回填树苗

- 状态：已采纳（2026-10-31）
- 影响面：§6.2、§6.4、§11.9
- 依赖：ADR-0011（真实生成树再拆）

## 背景

ADR-0011 决定「真生成一棵树再拆掉」。这带来两个原文档没有的问题：

1. 压缩农业要不要保留原版树苗的**两阶段**生长（先 `STAGE 0 → 1`，下一次才 `growTree`）？
2. 树被拆掉之后，原地留下什么？

## 已验证的原版事实

`SaplingBlock.advanceTree`：

```java
public void advanceTree(ServerLevel level, BlockPos pos, BlockState state, RandomSource random) {
    if (state.getValue(STAGE) == 0) {
        level.setBlock(pos, state.cycle(STAGE), 4);   // 0 → 1，什么都不长
    } else {
        this.treeGrower.growTree(level, level.getChunkSource().getGenerator(), pos, state, random);
    }
}
```

`SaplingBlock.randomTick`：`getMaxLocalRawBrightness(pos.above()) >= 9 && random.nextInt(7) == 0` 才调 `advanceTree`。

`TreeGrower.growTree` 的 2×2 搜索：

```java
for (int x = 0; x >= -1; x--) {
    for (int z = 0; z >= -1; z--) {
        if (isTwoByTwoSapling(state, level, pos, x, z)) { ... }
    }
}
```

**注意**：`x` 与 `z` 都是 `0, -1`，即**四棵树苗中任意一格都可以作为锚点**，遍历顺序是 (0,0) → (0,-1) → (-1,0) → (-1,-1)。这与方案 §6.2 第 2 条写的「东南 → 东北 → 西南 → 西北」在**语义上一致**（相对 `pos` 的偏移），但表述容易读成「固定从东南角开始」。实际是「从 `pos` 自身开始，向负 X / 负 Z 扩展」。

`isTwoByTwoSapling` 只比较 `Block` 相同（`level.getBlockState(...).is(block)`），不比较 `STAGE`。文档 §6.2 第 3 条「比较 `Block` 相同，不比较 ID 列表」正确。

`growTree` 成功时把四格都 `setBlock(AIR, 4)`；失败时把四格都恢复成**传入的那个 `state`**（同一份）。

## 决策一：保留两阶段

压缩树苗与原版树苗完全一致地走 `STAGE 0 → 1 → growTree`。不跳过、不加速。

## 决策二：拆树后回填树苗

### 单格树（1×1）

树被拆完后，在**原树苗位置**放回一棵同种树苗，`STAGE = 0`（从零开始下一轮）。

### 2×2 巨树

树被拆完后，**四格全部放回同种树苗，`STAGE = 0`**。

## 理由

**为什么保留两阶段**

- 原版节奏是「两次随机刻才长一棵」，跳过等于双倍加速。压缩农业的卖点是「用面积换产量」，不是「让时间变快」，加速会破坏平衡。
- 保留不需要额外代码——原版逻辑本就在跑，我们只是接管产物。

**为什么四格全放回**

- 玩家摆 2×2 的目的是长巨树。若只还一格，下次只能长出普通树，玩家得手动补三格——每次都要人工干预，违背「种一次就不用管」。
- 四格下方的压缩方块等级可以不同（ADR-0004 允许），产物进西北那个 BE，但**回填不看等级**：四格都放回。
- 若按「原来哪几格是压缩方块就放哪几格」回填，玩家挪走一格压缩方块后会导致永久少一格，行为随配置漂移，不可预测。

**为什么 `STAGE` 重置为 0 而不是保持**

- `growTree` 成功时四格已被 `setBlock(AIR)`。我们放回的是新方块，`STAGE` 从默认值 0 起。
- 若保持 `STAGE = 1`，下一轮树苗会立刻满足 `growTree` 条件，变成「拆了就马上再长」，等于无限循环加速。这是必须避免的。

## 后果

- **回填必须是原子操作，且不能触发无限套娃**：回填的树苗放在原位后，会立即被本模组的识别逻辑看到（它属于 `#saplings`、下方是压缩方块）。这是**预期行为**——它就是下一轮的种子。但要确保「回填」这个动作本身不会触发一次结算事件。
- 树拆完后若原位置已被其他方块占据（玩家在拆树瞬间放了东西、或树的生成又碰到了别的东西），**不回填、也不覆盖**。宁可少一棵树苗，不可毁玩家方块。
- §6.2 第 6 条「成功 → DENY 原版巨树生成 → 结算 → 重置四格树苗 stage=0」必须重写为：「允许原版生长 → 记录方块 → 取掉落 → 拆树 → 四格回填新树苗 `STAGE=0` ∘ 结算」。顺序上先拆后填，避免回填的树苗被拆树逻辑误删。
- §6.4 的「木质破坏音效 + 粒子」现在对应「一次真实的树被拆掉」，语义正确，无需修改。
- `isTwoByTwoSapling` 只比 `Block`，所以四格树苗可以是不同 `STAGE` 的（比如一格已 `STAGE 1`、三格 `STAGE 0`），原版照样认得。回填时统一置 0，行为可预测。
